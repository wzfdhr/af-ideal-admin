# Typed coordinate fields

Form schema v2 input widgets may explicitly declare `config.valueType: 'coordinate'` and `config.coordinateAxis: 'longitude' | 'latitude'`. No implicit conversion of text, integer, or money fields occurs. Form v1 still rejects this declaration. Existing integer and decimal fields retain nonnegative quantity and exact two-decimal money semantics.

The authoritative parser accepts decimal strings with an optional minus sign, one to three integer digits (no leading zeroes), and at most six fractional digits. Longitude is bounded by [-180, 180], latitude by [-90, 90]. Bounds use integer microdegrees, so values one microdegree beyond either endpoint are rejected without rounding. Numbers, booleans, arrays, objects, NaN, infinity, exponent notation, scripts, plus signs, whitespace and trailing content are rejected. Missing optional values stay absent; no point is invented. Accepted values become canonical strings: trailing fractional zeroes disappear and negative zero becomes `"0"`. Revalidation after save/read is idempotent. Defaults are validated and canonicalized during schema parsing without mutating the caller's schema.

Only input widgets support coordinates. Axis is mandatory and cannot be attached to other value types. Coordinate min/max overrides and arbitrary precision declarations are rejected. The runtime retains text input and allows the full eleven-character signed six-digit format independently of legacy text length limits. The field editor explicitly selects the type and axis and upgrades the form to v2. Changing to coordinates clears previous min/max and validation rules; remaining invalid defaults and dependent rules must be corrected before publication.

Coordinates cannot act as existing form condition drivers, use field comparison/text-validation rules, participate in quantity-times-price computed fields, or be exposed as workflow predicate candidates. Workflow binding validation rejects forged references through the existing typed field allowlist. Coordinates may themselves have visibility/required conditions driven by other supported fields.

Reporting catalogues and frozen field maps retain both coordinate type and axis. SQL projects only canonical, axis-bounded strings, with a guarded numeric cast; corrupt persisted values become NULL. Numeric sorting uses the checked projection. Map consumers convert validated strings to display numbers and enforce axis role; they must not interpret ordinary text as coordinates. Excel export uses numeric cells with six optional fractional digits, retaining signed coordinate precision while money keeps its two-decimal format. Existing field visibility/redaction controls apply unchanged.

This change adds no database migration or alternate write transaction. Record writes continue through existing transactional validation, revisions and idempotency handling. It does not heal older text or numeric records, rewrite released snapshots, or invent coordinates for missing data. Rollback to a server that predates this type cannot read new coordinate schemas; retain the new parser while such releases exist, or explicitly retire the new releases and restore a compatible release first. Do not silently relabel coordinates as money during rollback.

Evidence is separated: contract tests cover exact bounds, rejection, JSON save/reopen and existing money behavior; component tests cover type/axis editing, schema export/import, text input and validators; export tests inspect generated workbook types and formats. Database-backed map/report queries and native browser acceptance belong to the parent integration lane; component tests are not proof of those runtime paths.
