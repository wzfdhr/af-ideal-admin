# 企业级中后台框架任务清单与验收标准

本文档基于以下两份文档制定：

- `docs/architecture/enterprise-admin-framework-roadmap.md`
- `docs/superpowers/plans/2026-06-22-enterprise-admin-framework.md`

目标不是把项目做成“能跑的后台模板”，而是升级为可在企业项目中复用、二次开发、接入真实后端、稳定交付和持续演进的中后台框架。

## 总体验收口径

所有任务默认遵守以下企业级开发标准。任何任务只要不满足这些标准，就不能进入“完成”状态。

### 代码质量门禁

- TypeScript 保持 `strict: true`。
- 新增核心代码不得使用 `any`；确有必要时必须在代码评审中说明边界和替代方案。
- 新增模块必须有清晰职责，避免把请求、状态、权限、视图逻辑混在一个文件里。
- 公共能力必须有类型定义、测试和文档。
- 公共能力必须提供 Mock 虚拟数据交互，不能只写静态页面。
- 不允许把构建产物、依赖压缩包、环境私密信息提交进仓库。
- 不允许新增无主的调试日志、`console.log`、`debugger`。
- 命名必须表达业务意图，避免临时命名、拼音缩写和含糊变量名。

### 测试门禁

- 核心工具函数、权限逻辑、请求封装、菜单过滤、表单 schema 迁移必须有单元测试。
- 涉及用户登录、路由跳转、权限控制、菜单渲染、表单提交的改动必须有回归验证。
- 修复缺陷必须先补能复现问题的测试，再实现修复。
- 每个阶段至少通过：

```bash
npm run lint:check
npm run typecheck
npm run test
npm run build:prd
```

- 发布前必须补充或更新 e2e smoke 测试。

### Mock 数据门禁

- 所有页面能力必须能在无后端环境下通过 Mock 完成增删改查或核心交互。
- Mock 接口结构必须与真实 API 契约一致。
- Mock 必须覆盖成功、空数据、未登录、无权限、业务错误、服务端错误、超时场景。
- 涉及列表的 Mock 必须支持分页、查询、排序或明确说明不支持排序的原因。
- 涉及权限的 Mock 必须支持至少管理员、普通用户、受限用户三种角色场景。
- 涉及租户或组织的数据必须能模拟不同租户、部门、岗位的数据范围。
- e2e smoke 测试优先使用稳定 Mock 数据，避免依赖真实后端状态。

### 安全门禁

- 认证 token 的读取、写入、清理只能通过统一 auth 服务完成。
- 请求层必须统一处理 401、403、业务错误、网络错误和服务端异常。
- 权限判断必须在路由、菜单、按钮三个入口使用同一套访问引擎。
- 服务端菜单不得直接执行后端传入的组件路径，必须使用前端白名单组件 key 映射。
- 表单设计器不得执行用户输入的表达式或脚本。
- 远程数据源必须具备白名单、超时、错误态和响应适配。

### 交付门禁

- 每个任务必须有可审查的提交，提交信息遵守 Conventional Commits。
- 每个 PR 必须说明变更范围、测试结果、风险点和回滚方式。
- 新增能力必须同步文档。
- CI 必须通过后才能合并。
- 影响接口契约、权限契约、表单 schema 的改动必须写迁移说明。

## 阶段 P0：仓库治理与交付基线

目标：让项目仓库干净、构建可复现、分支可维护、CI 可依赖。

### T-001 同步本地与远端主线

**优先级：P0**

**交付物**

- 本地 `framework` 与 `origin/framework` 对齐。
- 本地无未提交变更。

**验收标准**

- `git status --short --branch` 显示本地分支不再 `ahead` 或 `behind`。
- `git diff --stat HEAD..origin/framework` 无输出。
- `git diff --stat origin/framework..HEAD` 无输出。
- 不丢失用户未提交代码。

### T-002 清理生成产物和依赖压缩包

**优先级：P0**

**交付物**

- 删除 `dist.zip`。
- 删除 `node_modules.zip`。
- `.gitignore` 明确忽略 `dist/`、`node_modules/`、构建压缩包和本地临时文件。

**验收标准**

- `git ls-files | rg "dist.zip|node_modules.zip"` 无输出。
- `git status --short` 只包含本任务预期文件。
- `npm ci` 后不会产生需要提交的依赖目录变更。

### T-003 清理远端无用分支

**优先级：P0**

**交付物**

- 删除已合入主线的远端工作分支。
- 删除确认废弃的历史分支。

**验收标准**

- `git branch -r --merged origin/framework` 中不再出现已废弃工作分支。
- `git branch -r` 只保留当前主线、活跃开发分支和明确需要保留的发布分支。
- 删除分支前已确认对应提交在 `origin/framework` 或被明确标记为废弃。

### T-004 固定包管理器和运行时版本

**优先级：P0**

**交付物**

- 明确 npm 为默认包管理器。
- 保留单一 lockfile：`package-lock.json`。
- README 和 CI 使用相同安装命令。
- 增加 Node 版本说明或 `.nvmrc`。

**验收标准**

- 仓库不存在 `pnpm-lock.yaml`、`yarn.lock` 等混用 lockfile。
- `npm ci` 在干净环境中可成功安装。
- CI 和文档里的安装命令一致。

### T-005 强化 CI 质量门禁

**优先级：P0**

**交付物**

- CI 至少包含 lint、typecheck、unit test、build、e2e smoke。
- 不同检查拆成独立步骤，失败原因可快速定位。

**验收标准**

- PR 和推送到主线都会触发 CI。
- 任意一项检查失败时 PR 不允许合并。
- CI 使用 `npm ci`，不使用本地缓存产物替代依赖安装。

## 阶段 P1：请求、认证与权限核心

目标：让框架可以安全接入真实后端，并支撑企业权限模型。

### T-101 建立独立请求客户端

**优先级：P0**

**交付物**

- 新增 `src/api/request-client.ts`。
- `src/api/request.ts` 改为导出默认 request 实例。
- 业务 API 逐步从全局 axios 迁移到 request 实例。

**验收标准**

- 不再依赖 `axios.defaults.baseURL` 作为全局副作用。
- 请求客户端支持 baseURL、timeout、auth header 配置。
- 请求客户端有单元测试覆盖实例创建和 token 注入。
- 现有登录、用户信息、业务列表接口行为不回退。

### T-102 统一 API 响应和错误协议

**优先级：P0**

**交付物**

- 定义 `ApiResponse<T>`。
- 统一处理成功、业务错误、401、403、404、500、网络异常。
- 错误信息支持 `traceId` 展示。

**验收标准**

- 业务错误不会被当作网络错误处理。
- 401 会清理登录态并跳转登录页。
- 403 会进入无权限页或弹出明确权限提示。
- 错误提示不泄露 token、密码、请求头等敏感信息。
- 单元测试覆盖成功响应、业务失败、未登录、无权限和网络异常。

### T-103 建立认证服务边界

**优先级：P0**

**交付物**

- 新增 `src/services/auth.ts`。
- token、用户信息、登出清理统一走 auth 服务。
- Pinia user store 不直接散落处理 token 存储细节。

**验收标准**

- 登录成功后 token 只通过 auth 服务写入。
- 登出后 token、用户信息、菜单缓存、路由监听全部清理。
- 认证失败时不会残留半登录状态。
- 单元测试覆盖登录态写入、读取、清理和失败回滚。

### T-104 建立统一访问控制服务

**优先级：P0**

**交付物**

- 新增 `src/services/access.ts`。
- 支持 `roles`、`permissions`、`mode: all | any`。
- 兼容现有 `meta.roles`，逐步迁移到 `meta.access`。

**验收标准**

- 路由、菜单、按钮共用同一访问判断函数。
- 支持通配符 `*`。
- 支持任一权限匹配和全部权限匹配。
- 单元测试覆盖角色、权限码、通配符、父子路由继承。

### T-105 升级按钮权限为权限码模型

**优先级：P1**

**交付物**

- `v-allow` 或新指令支持权限码，例如 `user:create`。
- 保留兼容层或提供迁移说明。
- 新增 `PermissionButton` 组件作为推荐入口。

**验收标准**

- 无权限按钮不会渲染或会展示明确禁用态。
- 按钮权限不再只依赖单一角色名。
- 权限码命名规范写入文档。
- 单元测试覆盖有权限、无权限、通配符和空权限场景。

### T-106 完成服务端菜单模式

**优先级：P0**

**交付物**

- 完成 `menuFromServer = true` 下的菜单拉取、过滤和路由访问判断。
- 后端菜单使用组件 key，前端通过白名单映射到本地组件。
- 菜单、路由、权限契约写入文档。

**验收标准**

- 服务端返回不存在的菜单 name 时不会导致页面异常。
- 服务端返回未授权菜单时前端不会展示。
- 直接访问未授权路由会进入无权限或 404 页面。
- 单元测试覆盖菜单 flatten、权限过滤和非法菜单处理。

### T-107 迁移现有 API 模块到统一 request

**优先级：P1**

**交付物**

- `src/api/user.ts`、`src/api/business.ts`、`src/api/common.ts` 使用统一 request。
- API 返回类型与 `ApiResponse<T>` 兼容。

**验收标准**

- `rg "import axios from 'axios'" src/api` 无业务 API 直接导入。
- 现有单测和登录流程不回退。
- API 函数命名、参数、返回类型清晰稳定。

### T-108 建设 Mock 虚拟数据平台

**优先级：P0**

**交付物**

- 重构 `src/mock` 为模块化结构。
- 建立统一 response helper。
- 建立 seed 数据和场景数据。
- 覆盖 auth、user、permission、menu、dictionary、business 基础域。

**验收标准**

- 所有现有页面在无后端环境下可完成主要交互。
- Mock 支持分页、详情、新增、编辑、删除、批量操作的模拟。
- Mock 支持 401、403、500、空数据、超时、业务错误场景。
- 权限相关 Mock 支持管理员、普通用户、受限用户。
- Mock 数据结构与 API 类型定义一致。

### T-109 建立 Mock 场景切换机制

**优先级：P1**

**交付物**

- 支持切换 Mock 场景：管理员、普通用户、受限用户、租户 A、租户 B、异常状态。
- 支持开发者重置 Mock 数据。
- 支持 e2e 指定固定 Mock 场景。

**验收标准**

- 切换角色后菜单、按钮、路由和数据范围同步变化。
- 切换租户后品牌、菜单、数据范围可模拟差异。
- e2e 测试可使用稳定场景，不依赖手工登录后状态。

## 阶段 P2：业务组件层与基础模块

目标：减少重复业务页面代码，形成企业中后台标准开发范式，并让底层 UI 组件库具备后续从 Arco 平滑切换到 `aheart-ui` 的能力。

### T-200 建设可替换 UI 底座边界

**优先级：P0**

**交付物**

- 新增 `src/components/pro-ui` 适配层。
- 新增 Arco adapter，作为当前稳定交付实现。
- 新增 `docs/architecture/ui-library-strategy.md`。
- 明确 `aheart-ui` 与主项目同步推进，但不得在企业级能力成熟前直接替换 Arco。
- 形成 `aheart-ui` 企业级可替换验收清单。

**验收标准**

- 新增企业级业务页面不得直接依赖底层 UI 库的私有 API，必须优先使用 `ProTable`、`ProForm`、`CrudPage`、`PermissionButton`、`DictSelect` 等内部业务组件。
- `src/components/pro-ui` 暴露稳定 adapter contract，至少包含 Button、Table、Form、FormItem、Input、Select、Modal、Drawer、Message。
- 当前实现由 Arco adapter 提供，未来 `aheart-ui` adapter 可在不重写业务页面的前提下逐步替换。
- `aheart-ui` 只有在核心组件、主题、无障碍、文档、单测、视觉回归、e2e smoke 和 Mock 交互示例全部达标后，才允许进入核心模块替换。
- 至少一个 Mock-backed 示例页面通过 Pro 组件验证列表、表单、权限按钮、错误态和空状态，不允许只做静态展示。
- 单元测试覆盖 adapter contract 的存在性和消息能力。

### T-201 建设 ProTable 基础能力

**优先级：P1**

**交付物**

- 新增 `src/components/pro-table`。
- 支持列 schema、分页、loading、空状态、查询参数、刷新。

**验收标准**

- 页面不需要手写重复分页和 loading 状态。
- `fetchData` 入参和出参有类型约束。
- 首屏加载、分页切换、查询重置都有测试或示例覆盖。
- 组件文档包含最小用法和服务端分页用法。

### T-202 建设 ProForm 基础能力

**优先级：P1**

**交付物**

- 新增 `src/components/pro-form`。
- 支持 schema 字段、默认值、校验、提交、重置、只读模式。

**验收标准**

- 表单字段有稳定类型定义。
- 异步选项、必填校验、提交 loading、错误提示行为一致。
- 新增表单页面不需要重复写通用校验和提交生命周期。
- 单元测试覆盖默认值、校验失败、提交成功和只读模式。

### T-203 建设字典组件和字典服务

**优先级：P1**

**交付物**

- 字典服务统一缓存静态和远程字典。
- 新增 `DictSelect`、`DictRadio` 等组件。

**验收标准**

- 字典请求不会在同一页面重复触发。
- 字典加载失败有明确错误态。
- 表格显示和表单选择使用同一字典源。
- 字典文档包含接口契约和使用示例。

### T-204 改造系统管理模块

**优先级：P2**

**交付物**

- 用户、角色、菜单、部门、字典页面改用 ProTable、ProForm、权限按钮。
- 每个模块拥有 API 类型、权限码、路由元数据和测试。

**验收标准**

- 页面支持查询、分页、新增、编辑、删除、详情。
- 操作按钮受权限码控制。
- 删除和危险操作有二次确认。
- 失败场景有明确提示，不吞异常。
- CRUD 页面开发规范可复用到新业务模块。

## 阶段 P3：表单设计器产品化

目标：让表单设计器具备生产可用的 schema、迁移、安全和运行时能力。

### T-301 建立版本化表单 Schema

**优先级：P1**

**交付物**

- 新增 `src/components/form-designer/schema`。
- schema 包含 `version`。
- 提供 `migrateFormSchema`。

**验收标准**

- 旧 schema 可被迁移到当前版本。
- 缺失字段会补默认值，不导致运行时崩溃。
- 单元测试覆盖 legacy schema、当前 schema 和非法 schema。

### T-302 拆分设计器与运行时渲染器

**优先级：P1**

**交付物**

- `designer` 只负责编辑、拖拽、配置。
- `renderer` 只负责生产渲染、校验、提交。
- 公共 schema 类型放在 `schema` 层。

**验收标准**

- 业务页面可只引入 renderer，不打包设计器编辑能力。
- 设计器改动不影响生产渲染器 API。
- 核心 widget 渲染有测试覆盖。

### T-303 远程数据源安全治理

**优先级：P0**

**交付物**

- 数据源白名单。
- 参数映射。
- 超时和错误态。
- 响应适配器。

**验收标准**

- 用户无法通过表单 schema 请求任意外部地址。
- 远程选项请求失败时组件可恢复，不影响整个表单。
- 响应格式不匹配时有明确错误提示。
- 单元测试覆盖白名单拦截、成功加载、超时和格式错误。

### T-304 表单导入、导出、预览和发布

**优先级：P2**

**交付物**

- schema JSON 导入。
- schema JSON 导出。
- 预览模式。
- 发布和回滚接口预留。

**验收标准**

- 导入非法 JSON 不会污染当前表单。
- 导出的 schema 可再次导入并保持等价。
- 预览和生产 renderer 使用同一渲染逻辑。
- 发布前执行 schema 校验。

### T-305 表单设计器 Mock 数据闭环

**优先级：P1**

**交付物**

- Mock 表单 schema 列表、详情、保存、发布、回滚接口。
- Mock 表单提交接口。
- Mock 远程选项接口。

**验收标准**

- 表单设计器可在无后端环境下完成创建、编辑、保存、预览、发布。
- 运行时表单可通过 Mock 完成提交。
- 远程选项支持成功、空数据、失败、超时场景。

## 阶段 P3.5：流程设计器、低代码与大屏扩展

目标：补齐企业级中后台平台化能力，形成从表单、流程、页面到数据展示的完整模拟闭环。

### T-351 流程设计器 MVP

**优先级：P1**

**交付物**

- 基于 AntV X6 的流程设计器页面。
- 支持开始、审批、抄送、条件、并行、结束节点。
- 节点属性配置面板。
- 流程定义保存、预览、发布、停用。
- Mock 流程定义、流程实例、待办、已办、审批记录。

**验收标准**

- 可拖拽创建流程图。
- 可配置节点名称、审批人、条件、绑定表单。
- 可通过 Mock 发起流程、审批、驳回、转交、撤回。
- 无权限用户不能发布流程。
- 流程 schema 有版本号和校验。

### T-352 低代码页面搭建 MVP

**优先级：P2**

**交付物**

- 低代码页面 schema。
- 物料注册机制。
- 页面设计器基础画布。
- 支持 ProTable、ProForm、图表卡片、统计卡片物料。
- Mock 页面保存、预览、发布、回滚接口。

**验收标准**

- 可通过拖拽或配置生成一个查询表格页面。
- 页面组件可绑定 Mock 数据源。
- 按钮可绑定查询、提交、跳转、打开弹窗、刷新区块事件。
- 页面可预览、保存、发布和回滚。
- 页面、区块、按钮均支持权限码。

### T-353 大屏可视化 MVP

**优先级：P2**

**交付物**

- 大屏设计画布。
- 图表物料：折线、柱状、饼图、排行、指标卡、滚动表格。
- Mock 实时数据源。
- 大屏预览和全屏播放。

**验收标准**

- 可配置一个完整 1920x1080 大屏。
- 图表可绑定 Mock 数据并定时刷新。
- 支持暗色主题和企业品牌色。
- 支持空数据、异常数据和告警滚动场景。

### T-354 报表中心 MVP

**优先级：P2**

**交付物**

- 报表列表。
- 报表详情。
- 查询条件。
- 图表和明细表。

**验收标准**

## 阶段 P4：可观测性、安全与运维

目标：让框架上线后可诊断、可审计、可治理。

### T-401 前端错误边界和异常上报

**优先级：P1**

**交付物**

- Vue error handler。
- 路由错误捕获。
- 请求错误上报入口。
- 白屏检测方案。

**验收标准**

- 运行时异常不会造成无提示白屏。
- 错误日志包含路由、用户标识、traceId、版本号。
- 不上报 token、密码、身份证号等敏感信息。

### T-402 操作审计与安全事件

**优先级：P2**

**交付物**

- 登录、退出、权限变更、菜单变更、关键操作的审计示例。
- 审计接口契约文档。

**验收标准**

- 关键操作能定位操作者、时间、对象、结果。
- 审计失败不阻断主业务，但必须可观测。
- 文档明确前端和后端的责任边界。

### T-403 部署模板和运行时配置

**优先级：P1**

**交付物**

- Nginx history fallback 示例。
- API 网关转发示例。
- Docker 或静态托管部署说明。
- 环境变量说明。

**验收标准**

- 刷新任意前端路由不会 404。
- `/api` 可按环境转发到后端。
- 生产构建不依赖 Vite dev proxy。
- 部署文档可被新成员独立执行。

### T-404 审计日志 Mock 闭环

**优先级：P1**

**交付物**

- Mock 登录日志、操作日志、权限变更日志、导出日志。
- 审计日志查询页面。
- 审计接口契约文档。

**验收标准**

- 可按用户、模块、时间、结果查询审计日志。
- 权限变更、流程发布、表单发布、大屏发布都可产生日志模拟。
- 审计日志不展示敏感 token 和密码。

## 里程碑验收标准

### M1：企业级地基完成

包含任务：T-001 到 T-107。

验收标准：

- 仓库无生成产物。
- 本地和远端主线同步。
- 请求、认证、权限有统一边界。
- 服务端菜单模式可用。
- 路由、菜单、按钮权限行为一致。
- `npm run lint:check`、`npm run typecheck`、`npm run test`、`npm run build:prd` 全部通过。

### M2：企业级业务开发范式完成

包含任务：T-200 到 T-204。

验收标准：

- UI 底座有明确 adapter 边界，新页面不直接绑定底层 UI 库。
- 至少一个系统管理模块使用 ProTable 和 ProForm 改造完成。
- 新增 CRUD 页面有清晰开发指南。
- 权限按钮、字典、查询表格、编辑表单形成标准范式。
- 新业务模块可以在一天内完成 API、路由、菜单、页面、权限、测试的基础闭环。

### M3：表单设计器生产可用

包含任务：T-301 到 T-304。

验收标准：

- schema 有版本和迁移。
- 设计器和运行时渲染器边界清楚。
- 远程数据源安全策略落地。
- schema 导入、导出、预览可用。
- 不执行用户输入脚本。
- 表单设计器的列表、详情、保存、发布、提交、远程选项均可通过 Mock 完成演示。

### M3.5：平台化能力 MVP 完成

包含任务：T-351 到 T-354。

验收标准：

- 流程设计器可完成流程定义和流程实例 Mock 流转。
- 低代码页面搭建可生成至少一个查询表格页面。
- 大屏设计器可完成至少一个 Mock 实时数据大屏。
- 报表中心可完成至少三类 Mock 报表查询和导出任务模拟。
- 以上能力都接入权限码、Mock 数据和基础文档。

### M4：上线交付能力完成

包含任务：T-401 到 T-503。

验收标准：

- 有错误上报、审计示例、部署模板、发布流程。
- 文档覆盖开发、接后端、权限、部署、发布。
- CI 和代码评审流程能阻止低质量改动进入主线。

## 最终企业级验收标准

项目达到企业级中后台框架基线时，必须同时满足：

- 真实后端可按文档接入登录、用户信息、菜单、字典和业务接口。
- 所有核心能力都可在无后端环境下通过 Mock 虚拟数据完成演示和测试。
- 权限模型覆盖路由、菜单、按钮，并预留数据权限。
- 请求层支持统一错误处理、traceId、认证注入和后续多服务扩展。
- 至少一套完整 CRUD 模块可作为企业业务开发样板。
- 表单设计器具备版本化 schema、安全远程数据源和生产渲染能力。
- 流程设计器、低代码页面搭建、大屏可视化、报表中心至少具备 MVP 能力。
- CI 能拦截 lint、类型、单测、构建和 e2e smoke 回归。
- 文档足以支撑新成员独立完成页面开发和部署。
- 仓库不包含生成产物、依赖压缩包和敏感信息。
